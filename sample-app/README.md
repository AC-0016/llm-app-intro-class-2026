# 完成版サンプル

LLMの呼び出し方の基本と、LLMを使うWebアプリ4つの完成版です。
5つのフォルダは互いのファイルを参照せず、それぞれ単独で動きます。

| フォルダ | アプリ | 学ぶこと | ポート |
|---|---|---|---|
| `llm-call/` | LLM呼び出しの基本（ターミナルで動く） | 1回だけ呼ぶ方法と、会話の履歴をのせて呼ぶ方法 | なし |
| `chat-app/` | チャットアプリ | 会話の履歴をブラウザに持ち、毎回まとめて送る | 8000 |
| `keyword-app/` | キーワード検索アプリ | RAG：Janomeで資料を探し、その資料をもとにLLMが答える | 8001 |
| `vector-app/` | ベクトル検索アプリ | RAG：Embeddingで意味の近い資料を探し、その資料をもとにLLMが答える | 8002 |
| `progress-app/` | 制作の進捗アプリ | Function Calling：LLMが関数を選び、PythonがSQLiteを読み書きする | 8003 |

## 起動

毎回の授業開始時に、リポジトリのルートのターミナルでキーを非表示で入力し、同じターミナルから起動します。

```bash
export OPENAI_API_KEY=sk-********
cd sample-app/keyword-app   # ほかのアプリなら cd sample-app/chat-app など
python main.py
```

keyword-app と vector-app は、最初に1回 `python init_db.py` で資料のDB（`documents.db`）を作ってから `python main.py` を実行します。

`llm-call/` はWebサーバーを使わず、ターミナルで `python one_shot.py` または `python chat.py` を実行します。

チャットアプリはポート8000番、キーワード検索アプリは8001番、ベクトル検索アプリは8002番、進捗アプリは8003番をCodespacesの「ポート」タブから開きます。ポートは非公開のまま使います。
2つを同時に動かすときは、ターミナルを2つ使い、それぞれでキーを設定します。

- 常に実際のAPIを使います。質問するたびにAPI利用料金が発生します。
- 生成モデルは **gpt-6-luna**。Responses API、reasoning.effort=none、最大出力600トークンを使います。
- 終了時はサーバーをCtrl+Cで停止し、`unset OPENAI_API_KEY` を実行してターミナルを閉じます。
- キーは `.env`、Codespaces Secrets、シェルの設定ファイルに保存しません。

## LLM呼び出しの基本（llm-call）

```bash
cd sample-app/llm-call
python one_shot.py   # 1回だけ呼び出す
python chat.py       # 会話の履歴をのせて呼び出す（何も入力せずEnterで終わる）
```

### ファイルを読む順番

1. `one_shot.py` の `ask_once()`：質問の文字列だけを `input` に入れて送る
2. `chat.py` の `ask_with_history()` と `main()`：質問と回答を `history` のリストにため、毎回まとめて送る

2つの違いは `input` に入れるものだけです。指示文（各スクリプトの先頭にある `INSTRUCTIONS`）は同じです。

| | `one_shot.py` | `chat.py` |
|---|---|---|
| `input` に入れるもの | 今回の質問の文字列 | これまでの質問と回答のリスト |
| 前の会話 | 知らない | 知っている |
| 入力トークン数 | ほぼ一定 | 質問を重ねるたびに増える |

### 試すこと

1. `python one_shot.py` で「私の名前は佐藤です。」と送る。もう一度実行して「私の名前は？」と送る。→ 名前は分からない。
2. `python chat.py` で同じ2つを続けて送る。→ 前の会話を送っているので答えられる。
3. `chat.py` で質問を重ね、表示される入力トークン数が増えていくことを確かめる。

LLMそのものは前の会話を覚えていません。`store=False` でOpenAI側にも会話を保存しないため、覚えているように見えるのは、アプリが履歴を毎回送っているからです。
`chat.py` は履歴が長くなりすぎないよう、質問を最大10回（`MAX_TURNS`）までにしています。

## チャットアプリ（chat-app）

`llm-call/chat.py` をWebアプリにしたものです。

### ファイルを読む順番

1. `static/app.js`：`history` のリストに質問と回答をためる。送信のたびに `history` を全部サーバーへ送る
2. `main.py` の `chat()`：送られてきた履歴を確かめて、`ask_with_history()` を呼ぶ
3. `llm.py` の `ask_with_history()`：履歴のリストをそのまま `input` に入れてLLMへ送る

### 履歴をどこに持つか

履歴はブラウザの `history` 変数だけが持ち、サーバーは保存しません。そのため、次のようになります。

- 何人が同時に使っても、会話は混ざらない。
- ページを再読み込みすると、履歴は消える（「会話をリセット」と同じ）。
- 送られてくる履歴は書き換えられる可能性がある。サーバーは、役割が `user`・`assistant` のどちらかか、最後が質問か、長さと回数が上限内かを確かめる。

1つの会話の質問は最大10回です（`main.py` と `app.js` の `MAX_TURNS`。2か所を同じ値にします）。

### 試すこと

1. 「私の名前は佐藤です。」の次に「私の名前は？」と送る。→ 答えられる。
2. 「会話をリセット」を押して、もう一度「私の名前は？」と送る。→ 答えられない。
3. 質問を重ねて、画面下に表示される入力トークン数が増えていくことを確かめる。

## キーワード検索アプリ（keyword-app）

### ファイルを読む順番

1. `init_db.py`：Marp形式のスライド（`data/*.md`）をスライド1枚ずつに分け、Janomeで単語に分けて `documents.db` に保存する
2. `main.py` の `load_documents()`：起動時にDBから資料と単語を読み込む
3. `main.py` の `ask()`：質問を受け取り、①検索語を取り出す ②資料を探す ③LLMに答えさせる
4. `search.py`：Janomeで単語を取り出し、一致した数で資料を並べる
5. `llm.py`：資料と質問をLLMに送る
6. `static/app.js` の `askQuestion()`：送信と表示

### 検索の仕組み

1. `extract_words()` が質問をJanomeで単語に分け、名詞・動詞・形容詞の基本形を取り出す。
   助詞・記号、「の」のような意味の薄い語、「する」のようにどこにでも出る語は除く。
2. `search_documents()` が、各資料の単語（`init_db.py` が同じ `extract_words()` で作ってDBに保存したもの）に、質問の単語がいくつ含まれるかを数える。
   資料の形態素解析は `init_db.py` で1回だけ行うので、質問のときは質問だけを解析すればよい。
3. 一致した数の多い順に、上位3件（`main.py` の `TOP_K`）をLLMへ渡す。1件も無ければAPIを呼ばない。

| 質問 | 取り出される検索語 | 見つかるスライド（上位） |
|---|---|---|
| 学習と推論の違いは？ | 学習, 推論, 違い | 12枚目「学習と推論」 |
| TransformerのAttentionとは？ | transformer, attention | 9枚目「Transformerの考え方」 |
| ハルシネーションとは？ | ハルシネーション | 19枚目「得意なことと、確認が必要なこと」 |

単語の表記が違うと一致しません（例：「保管」と「保存」）。意味の近さは判定しないため、言い換えた質問では資料が見つからない場合があります。

## 資料（Marp形式のスライド）

keyword-app と vector-app は、それぞれの `data/` にある第1回のスライド（`session01/slides01.md` のコピー、`session01.md`）を資料にします。
`init_db.py` がMarp形式のMarkdownを次のように読み、DBに保存します。

| Markdownの書き方 | 資料としての扱い |
|---|---|
| 先頭の `---` から `---` まで | スライドの設定なので読まない |
| `---` だけの行 | スライドの区切り。スライド1枚が資料1つになる |
| 最初のスライドの `# 見出し` | 全スライドの題名（資料名） |
| 各スライドの最初の `#` / `##` 見出し | そのスライドの見出し |
| `<!-- コメント -->` | 発表者メモや出典なので読まない |
| `![画像](…)` | 画像なので読まない |
| ```` ``` ```` で囲まれたコード | 中の `#` や `---` も含め、本文としてそのまま読む |

- スライド1枚の本文は1000文字以内にします。超えると、DBを変える前に `init_db.py` が止まります。
- スライドを足したり直したりしたら、サーバーを止めて `python init_db.py` を実行し、サーバーを起動し直します。
- `init_db.py` は実行するたびに `documents` テーブルを作り直します。古い資料は残りません。
- keyword-app で `search.py` の単語の取り出し方（`STOP_WORDS` など）を変えたときも、`python init_db.py` で単語を作り直します。
- `session01/slides01.md` を直しても、`data/` のコピーは変わりません。必要ならコピーし直します。
- 資料IDは `init_db.py` が順番に付けるため、スライドを増減すると変わります。評価にはファイル名と何枚目かも記録します。

### DBのスキーマ（`documents.db` の `documents` テーブル）

| 列 | 型 | 内容 |
|---|---|---|
| id | INTEGER | 資料ID（1から順に付ける） |
| source | TEXT | 元のファイル名（例：`session01.md`） |
| slide | INTEGER | 何枚目のスライドか（Marpのページ番号と同じ） |
| title | TEXT | スライド全体の題名（最初のスライドの見出し） |
| heading | TEXT | そのスライドの見出し |
| body | TEXT | そのスライドの本文 |
| words | TEXT | keyword-appのみ。題名・見出し・本文から取り出した検索用の単語のリストを、JSONの文字列にしたもの（例：`["学習", "推論"]`） |
| vector | TEXT | vector-appのみ。ベクトル（数値のリスト）をJSONの文字列にしたもの |
| embedding_model | TEXT | vector-appのみ。ベクトルを作ったモデルの名前 |

## ベクトル検索アプリ（vector-app）

keyword-app と同じ形で、検索の部分だけをベクトル検索に変えたものです。2つを見比べると、違いが分かります。

### ファイルを読む順番

1. `init_db.py`：スライドを資料に分け、全部の資料をベクトルにして `documents.db` に保存する
2. `main.py`：起動時にDBから資料とベクトルを読み込む。`ask()` は ①質問をベクトルにする ②近い資料を探す ③LLMに答えさせる
3. `llm.py` の `embed_texts()`：Embedding APIで文章をベクトル（数値のリスト）にする
4. `search.py` の `cosine_similarity()`：2つのベクトルの向きの近さを計算する
5. `search.py` の `search_documents()`：類似度の高い順に資料を並べる
6. `static/`：keyword-app とほぼ同じ

### 検索の仕組み

1. `init_db.py` で、各スライドの「題名・見出し・本文」を `text-embedding-3-small` でベクトルにし、DBに保存しておく（1回のAPI呼び出し）。
2. 質問が来たら、質問も同じモデルでベクトルにする。
3. 質問のベクトルと各資料のベクトルのコサイン類似度を計算し、高い順に上位3件（`TOP_K`）をLLMへ渡す。
   類似度が0.3（`MIN_SIMILARITY`）より小さい資料は渡さない。この値は目安なので、画面に出る類似度を見て調整する。

| | keyword-app | vector-app |
|---|---|---|
| 比べ方 | 同じ単語がいくつあるか | ベクトルの向きがどれだけ近いか |
| 言い換え（「保管」と「保存」） | 見つからない | 見つかることがある |
| 検索にかかるAPI | なし | `init_db.py` の実行時に資料の分、質問のたびに質問の分 |
| `init_db.py` にAPIキー | いらない | 必要（資料をベクトルにするため） |

ベクトルはDBに保存するので、サーバーを再起動しても資料のEmbedding APIは呼びません。
`EMBEDDING_MODEL` を変えたときは、DBのベクトルと質問のベクトルを比べられないため、`main.py` が起動時に止まります。`python init_db.py` で作り直します。

## 制作の進捗アプリ（progress-app）

### ファイルを読む順番

1. `main.py` の `ask()`：質問を受け取り、`ask_with_tools()` を呼ぶ
2. `llm.py` の `ask_with_tools()`：LLMに関数を1つ選ばせ、結果を渡して回答させる（2回のAPI呼び出し）
3. `llm.py` の `run_tool()`：LLMが選んだ関数名と引数を確かめてから実行する
4. `progress_db.py`：SQLiteの `tasks` テーブルを作り、読み出す・追加する・完了フラグを変える
5. `static/app.js` の `askQuestion()`：送信と、関数の結果の表示

### 進捗DB

`progress-app/progress.db` の `tasks` テーブルに、Webアプリ制作の「やること」と完了フラグを保存します。

| 列 | 内容 |
|---|---|
| id | 番号 |
| task | やること |
| done | 完了フラグ。SQLiteに真偽値の型が無いため1（True）/0（False）で保存し、APIでは `true` / `false` で返す |

起動時に最初の6件を入れますが、すでにある行は上書きしません。初期値に戻すときは、サーバーを止めて `progress.db` を削除してから起動します。

### LLMが呼べる関数

| 関数 | 引数 | DB | すること |
|---|---|---|---|
| `get_tasks` | `status`（`all`・`todo`・`done`） | 読む | 進捗を調べる |
| `add_task` | `task`（100文字以内） | 書く | やることを未完了で追加する |
| `set_task_done` | `task_id`（整数）、`done`（`true`・`false`） | 書く | 完了フラグを指定した値にする |

- 完了フラグは「反対にする」ではなく「指定した値にする」関数にしています。LLMが同じ関数を2回呼んでも、元に戻ってしまわないようにするためです。
- 1つの質問で呼べる関数は1回だけです。そのため、完了フラグを変えるときは「id 4 のやることを完了にして」のようにidを指定します（idは「全部の作業を見せて」で確かめます）。「4番を完了にして」のように書くと、LLMがidかどうかを確かめようとして `get_tasks` を呼び、完了フラグを変えないまま終わることがあります。
- 実行するSQLは `progress_db.py` に書いた決まった文だけです。値は `?` で別に渡し、LLMが作った文字列をSQLに直接つなげません。
- 書き込む前に、型（整数か、`true`/`false` か）、文字数、そのidがあるかを確かめます。削除する関数は用意していません。

| 質問の例 | LLMが呼ぶはずの関数 |
|---|---|
| まだ終わっていない作業は？ | `get_tasks({"status":"todo"})` |
| 「READMEを書く」を追加して | `add_task({"task":"READMEを書く"})` |
| id 4 のやることを完了にして | `set_task_done({"task_id":4,"done":true})` |
| FastAPIとは？ | 関数を呼ばずに回答する場合がある |


## 書き方の方針

- Pydanticの入力モデルを除き、独自クラスや継承は使いません。
- 内包表記や複雑なコールバックを避け、for・if・辞書・普通の関数で書いています。
- 1つのファイルに1つの役割を持たせ、関数の先頭に何をするかを書いています。

## 範囲と限界

- 1問ずつ回答する。会話履歴やログインは実装しない。
- 回答の資料IDの正しさは自動では保証しない。実際の本文と照合する。
- プロンプトインジェクションの完全防御は保証しない。秘密は渡さない。書き込みは progress-app の追加と完了フラグの変更だけに限る。
- 利用回数の制限は実装しない。質問するたびにAPI利用料金が発生する。
- 本番公開には認証、利用者別の権限、利用量の管理などが必要。
- APIの応答にキーや環境変数を含めない。
- 授業案内・制作の進捗は架空のデータです。教材の文章は参照元の学習内容を踏まえて新規作成した復習ノートで、原文の転載ではありません。
